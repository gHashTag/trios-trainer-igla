WINDOW AUDIT - segment versus monolith
======================================

The question. Does re-executing ONE window of a run, warm-started from a
published checkpoint plus its resume record, reproduce the monolithic run
byte for byte? If it does not, a challenged window proves nothing and the
audit is theatre.

The answer measured here, on this machine, on this date: YES. The two
step-200 checkpoints are byte-identical, and so are the two step-200 resume
records - which is the stronger statement, because those carry the AdamW
moments and the batch-sampler state as well as the weights.

Read docs/WINDOW-AUDIT.md before quoting any of this. In particular: this is
a SAME-MACHINE claim. It says nothing about a different CPU architecture,
where the boundary documented in docs/CROSS-ARCH-DIVERGENCE.md is unchanged.

RUN A - MONOLITH, 0 -> 200
--------------------------
Exact command, from the repository root:

  env -u DATABASE_URL -u NEON_DATABASE_URL -u TRIOS_NEON_DSN \
      -u TRIOS_DATABASE_URL -u TRIOS_FORMAT_TYPE -u GF16_ENABLED \
      -u TRIOS_GF16_DISABLE -u TRIOS_GF16_FLOOR_EVERY -u HIDDEN_DIM \
      -u NUM_ATTN_LAYERS -u TRIOS_CHECKPOINT_INIT \
    TRIOS_CHECKPOINT_DIR=evidence/window-audit/monolith \
    TRIOS_CANON_NAME=window-audit-monolith \
    TRIOS_CHECKPOINT_EVERY=100 \
    ./target/release/trios-train --seed 47 --steps 200 --hidden 64 \
      --eval-every 50 \
      --train-data data/tiny_shakespeare_train_core.txt \
      --val-data data/tiny_shakespeare_val.txt

Result: exit 0, DONE: seed=47 bpb=3.7925 steps=200 opt=adamw
Reported val_bpb: step 50 = 4.3108, 100 = 3.8702, 150 = 3.7974, 200 = 3.7925


RUN B - SEGMENT, resumed at 100, 100 -> 200
-------------------------------------------
Same command with the same --steps 200 (the cosine schedule is a function of
(step, steps_total), so the segment must be given the ORIGINAL total), plus:

    TRIOS_CHECKPOINT_DIR=evidence/window-audit/segment \
    TRIOS_CANON_NAME=window-audit-segment \
    --resume-from evidence/window-audit/monolith/window-audit-monolith/100.bin

Result: exit 0, DONE: seed=47 bpb=3.7925 steps=200 opt=adamw
Reported val_bpb: step 150 = 3.7974, 200 = 3.7925 - identical to run A at the
same steps, to every printed digit.

The trainer announced the warm start on stderr:

  [resume] warm start from ".../100.bin" sha256=d25ea6d6... step=100 of 200
  [resume] restored 12 optimizer instances (221184 moment elements)

12 instances is the whole AdamW path: embed, ctx0..ctx5, proj, attn_down,
attn_up, head, attn_w.

WHAT WAS PUBLISHED, AND ONE THING THAT WAS CHANGED
--------------------------------------------------
The runs wrote into
  evidence/window-audit/monolith/window-audit-monolith/{100,200}.{bin,json,resume}
  evidence/window-audit/segment/window-audit-segment/200.{bin,json,resume}
Those files were COPIED to the flat names above and the directories removed,
so that `shasum -a 256 evidence/window-audit/*.bin` names them. The bytes were
not touched - the digests above are the digests the trainer printed at write
time, and they are unchanged. One consequence, stated rather than hidden: the
`path` field inside each .json still names the ORIGINAL directory, so it does
not match where the file now sits. Every other field in those sidecars,
including `sha256`, describes the file as published.

`python3 interop/triosckp_reader.py --verify-all evidence` reads the three new
(.bin, .json) pairs and passes: 16 pairs, 16 passed, 0 failed.

The resume records are NOT read by that verifier - it decodes TRIOSCKP only.
They are checked by `cargo test --release --test window_audit_resume`, which
re-runs this whole segment-versus-monolith comparison in a tempdir on a tiny
budget (8 steps, split at 4) and asserts byte equality.


WHAT THIS DOES NOT SHOW
-----------------------
* Not a cross-architecture claim. Both runs executed on the same aarch64
  macOS machine, in the same binary. The x86_64/aarch64 checkpoint divergence
  documented in docs/CROSS-ARCH-DIVERGENCE.md is untouched by this work, and
  a window re-executed on an auditor's own hardware can only be graded on
  metric agreement within a stated uncertainty budget - never on bit
  equality. See docs/WINDOW-AUDIT.md.
* Not a claim about the Muon path. TRIOSRSM version 1 serialises the AdamW
  instances only; `--resume-from` with --optimizer muon / muon-cwd is refused
  with a non-zero exit naming the state it cannot carry.
* Not a claim about a 1B model. 200 steps at hidden=64 is a demonstration of
  the MECHANISM at a size that fits in one sitting. What scales is the cost
  ratio, not this number.
