THE 12000-STEP HEADLINE LEARNING-RATE SCHEDULE ACROSS AN ISA CHANGE
58 of 12000 differing without cos_det, 0 of 12000 with it
Measured 2026-08-07. Probe: scripts/lr_schedule_isa_probe.py

==============================================================================
 THE SCOPE LIMIT, VERBATIM, AND IT MAY NOT BE DROPPED WHEN THESE ARE QUOTED
==============================================================================

ONE macOS host. ONE pinned toolchain. ONE working tree, with the --target
triple as the only variable that moved. The x86_64 arm ran under Rosetta 2
BINARY TRANSLATION, NOT NATIVE x86_64 SILICON, and Apple's x86_64 libm is not
glibc's. This constrains a native x86_64 Linux arm; it does not replace it.

n = 1 per arm for each dump. The dumps are pure functions of the binary - no
corpus, no checkpoint, no environment, no RNG - so a within-arm repeat would
re-run a deterministic program and is not the control that matters here. The
CONTROL that matters is the default arm, which is why both arms were run.

==============================================================================
 WHAT WAS MEASURED
==============================================================================

src/bin/lr_schedule_dump.rs prints one line per step for steps 1..=12000 of the
headline schedule (max_steps 12000, warmup 1200, base_lr 0.003), as the raw u32
bit pattern of each f32, by CALLING train_loop::cosine_lr rather than a replica
of it. Bits, not decimals: the question is byte-identity and a decimal
rendering rounds two different floats onto one string.

==============================================================================
 EXACT BUILD AND RUN COMMANDS
==============================================================================

Both arms are built with an EXPLICIT --target, including the one that is also
the host. `cargo build` and `cargo build --target <host triple>` are not the
same invocation and do not write to the same path; making both explicit is what
keeps the triple the only moving variable.

    cargo build --release --locked --target aarch64-apple-darwin \
        --bin lr_schedule_dump
    cargo build --release --locked --target x86_64-apple-darwin \
        --bin lr_schedule_dump
    cargo build --release --locked --target aarch64-apple-darwin \
        --bin lr_schedule_dump --features det-math
    cargo build --release --locked --target x86_64-apple-darwin \
        --bin lr_schedule_dump --features det-math

Each binary is copied to target/lr-schedule-probe/<name> the moment it is
built, hashed there, and RUN from there, because the default and det-math
builds write to the SAME cargo output path and would otherwise overwrite each
other. The probe re-hashes every binary after the runs and refuses to report if
one changed underneath it.

    target/lr-schedule-probe/lr_schedule_dump-aarch64-apple-darwin-<arm>
    /usr/bin/arch -x86_64 \
        target/lr-schedule-probe/lr_schedule_dump-x86_64-apple-darwin-<arm>

To reproduce both arms and the baseline assertion in one command:

    python3 scripts/lr_schedule_isa_probe.py --both

The default arm is checked against 58 / step 4041 / 3b25032e vs 3b25032d before
the det-math arm is read. If the baseline ever stops reproducing, the probe
exits 2 and says so rather than reporting a comparison against a control that
moved.

==============================================================================
 WHY THIS IS ABOUT cos_det AND NOT SOMETHING ELSE
==============================================================================

Both arms were run in the SAME working tree on the SAME host minutes apart,
after every edit. The default arm still reports 58 at step 4041 - the number
published before cos_det existed, and re-derived three times including once in
standalone C outside this repository. A cos_det that closed the gap in BOTH
builds would mean something other than cos_det moved and the measurement would
not be about cos_det at all. It did not.

WHAT IS MEASURED: the schedule, at 12000 steps, on this host, with the ISA as
the only variable. 58 -> 0.

WHAT IS NOT MEASURED: the 12000-step CHECKPOINT. The schedule is 12000 numbers;
the headline is 12000 optimizer steps of a whole model. Closing the schedule
removes the one site that was MEASURED to break the headline, at step 4041. It
does not establish that the checkpoint is byte-portable, and nothing in this
file should be read as saying it does. The longest cross-ISA checkpoint MATCH
that has been run remains TEN steps (evidence/det-math-isa/).

A TRAP, recorded because it produced a wrong number once. Anyone re-deriving
the 58 baseline in C must pass -ffp-contract=off. clang defaults to
-ffp-contract=on, and a contracted build of the same schedule expression
reports 3413 of 12000 differing, first at step 1203 - a ~59x larger effect than
libm's, and not a measurement of libm at all. rustc never contracts, so the
Rust numbers here do not carry this hazard.
