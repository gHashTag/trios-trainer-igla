HEADLINE CROSS-ISA RESULT AT 12000 STEPS
========================================

Four training runs of the same 12000-step configuration, differing only in
(a) the compiled instruction set and (b) whether the `det-math` feature was
enabled. The four checkpoint records in this directory are the deliverable.
The 852272-byte `.bin` artifacts themselves are NOT committed: `/checkpoints/`
is excluded by .gitignore:13 and each sidecar already carries the sha256 of
its own artifact, so the record is what a third party checks.

------------------

  det-math  x86_64   65f36543520c5b88cd419ae458fe965d15b11d5d620448b8dc2188b9087dbd45

  default   arm64 != x86_64   DIFFER

All four artifacts are 852272 bytes.

Record filenames in this directory:

  dm-arm64-12000.json    det-math aarch64   canon_name h12k-dm-arm

Each was copied byte-for-byte from

`.bin` it hashes lives on the machine that produced it.

Every sha256 above was re-derived on 2026-08-07 with
`shasum -a 256 checkpoints/isa-probe/headline-12000/*/12000.bin` and compared
against the `sha256` field the corresponding record states about itself. All
four agreed. The records are not transcriptions of a number from somewhere
else; each one was checked against the bytes it describes.


2. THE DET-MATH PAIR IS BYTE-IDENTICAL, THE DEFAULT PAIR IS NOT
---------------------------------------------------------------

The det-math pair is the result. Two builds of one working tree, one compiler,
one host, differing only in `--target`, ran 12000 gradient steps and wrote
byte-identical weights. The previously published cross-ISA MATCH from this
project reached ten steps; this reaches twelve thousand.

A second, independent signal points the same way. The evaluation numbers are
bit-identical across the det-math pair and are NOT bit-identical across the
default pair:

                        det-math arm64   det-math x86_64
  final_val_bpb         2.6494300365448  2.6494300365448   equal
  ema_bpb               2.684941291809082 2.684941291809082 equal
  val_bpb_stderr        0.05594641715288162 0.05594641715288162 equal

                        default arm64    default x86_64
  final_val_bpb         2.6347548961639404 2.6466174125671387  differ
  ema_bpb               2.6706762313842773 2.6813371181488037  differ
  val_bpb_stderr        0.053656626492738724 0.0559522807598114 differ

These are floats the trainer computed, not the container digest, so they are
not a restatement of line 1.


3. THE DEFAULT AARCH64 VALUE EQUALS THE PUBLISHED HEADLINE
-----------------------------------------------------------

CHECKED, not assumed:

  evidence/r9-headline/12000.json      sha256 8a86fe69...c186012c
  df-arm64-12000.json                  sha256 8a86fe69...c186012c
  equal

`final_val_bpb` also agrees exactly (2.6347548961639404), so the default
aarch64 arm of this experiment is the published headline run and not merely a
run that resembles it.

That comparison is worth reading twice, because the two records do NOT agree
about their inputs. The published headline and the default aarch64 arm here
differ in `source_sha256` (ce9aa66b... vs e7dc92f8...), in
`platform.remap_applied` (false vs true), in `platform.rustflags_source`
(absent vs cargo-config-toml), in `trainer.sha256` (two different binaries),
and in `git_dirty`/`git_untracked` (false/false vs true/true) -- and they
still produced the same 852272 bytes. MEASURED: those particular differences
did not move this artifact. NOT MEASURED, and not claimed: that they can never
move an artifact. `source_sha256` is not a tight predictor of the weights, and
this pair is the evidence for that statement rather than against it.

Note also that `platform.features` in the published headline record carries no
`det-math` key at all, while all four records here carry one explicitly
(`det-math=0` or `det-math=1`). The feature string grew an entry between the
two runs. A reader diffing the records will see it; it is not a discrepancy.

5. THE X86_64 ARM RAN UNDER ROSETTA 2, NOT ON X86_64 SILICON
-------------------------------------------------------------

Both x86_64 arms were executed by Rosetta 2 binary translation on an aarch64
macOS host (Darwin 25.5.0). No x86_64 processor executed these instructions.
Rosetta 2 is a translator, and a translator is free to implement an x86_64
floating-point operation by whatever aarch64 sequence produces the architected
result; it is not obliged to reproduce what an Intel or AMD part would do, and
nothing here measured whether it does.

The claim this directory supports is therefore about a TRANSLATED x86_64 arm
only. It must be re-run on native x86_64 Linux hardware before anyone
describes it as ISA portability in general. Until that run exists, "the
det-math build is byte-portable across ISA" is an overstatement of what was
measured; "the det-math build is byte-identical between aarch64-apple-darwin
and x86_64-apple-darwin-under-Rosetta-2 on one host at 12000 steps" is the
whole of it.

The cross-arch CI job (`.github/workflows/cross-arch-repro.yml`) is the arm
that would settle this, and it is red by design against the DEFAULT build.


6. WHY TWO RECORDS WITH THE SAME SHA256 ARE NOT THE SAME FILE
--------------------------------------------------------------

dm-arm64-12000.json and dm-x86_64-12000.json state the same `sha256` and are
not identical files. Of 64 leaf fields they differ in exactly six, and every
one of the six is derived from the host, the clock or the run name rather than
from the computation:

  canon_name       h12k-dm-arm  /  h12k-dm-x86
  path             .../h12k-dm-arm/12000.bin  /  .../h12k-dm-x86/12000.bin
  platform.arch    aarch64  /  x86_64
  trainer.path     outside-scope:tt-arm64-detmath  /  outside-scope:tt-x86-detmath
  trainer.sha256   64e8d9a8...d127c911  /  3ac5c08d...b0f61bf8
  ts               2026-08-06T19:21:22.586556+00:00 / 2026-08-06T19:23:00.917288+00:00

`trainer.sha256` differs because the two arms ARE two different binaries -- an
aarch64 executable and an x86_64 executable. That field differing is the
experiment working, not a flaw in it. `ts` differs because the four runs did
not finish at the same instant.

Every other field, including all 58 that describe the computation, is equal.

The default pair differs in those same six fields plus five that are results:
`sha256`, `final_val_bpb`, `min_observed_val_bpb`, `ema_bpb`, and
`val_bpb_stderr`.


7. SCOPE LIMITS, STATED SO THEY ARE NOT DISCOVERED LATER
---------------------------------------------------------

  a. TRANSLATED, NOT NATIVE. Section 5. This is the largest limit.

  b. DIRTY TREE. All four records carry `git_sha`
     e9eec901d22806c66d524f8f398a8d92fc64dc20 with `git_dirty: true` and
     `git_untracked: true`. The runs were made from a working tree that was
     modified relative to that commit. A third party checking out e9eec901
     clean is NOT guaranteed to reproduce these bytes, and no run in this
     directory demonstrates that they would. `scripts/headline_isa_probe.py`
     prints the git state of the tree it runs in for exactly this reason.

  c. ONE HOST, n=1 PER ARM. Each arm was run once. The within-arm repeat
     control that scripts/local_isa_probe.py carries was not re-run at 12000
     steps; the same-machine determinism it established was measured at ten
     steps and in CI, not here.

  d. FOUR CONCURRENT PROCESSES. The four arms were launched in parallel on one
     machine and waited on together. That affects wall-clock only -- no timing
     number is published from these runs, and none should be derived from
     their `ts` fields.

  e. SCHEMA. All four records are `trios-checkpoint-record/9`.


8. VERIFYING THIS DIRECTORY
----------------------------

  cargo test --release --test headline_isa_12000

That test re-reads all four records from the repository root and fails if any
of the four hashes, the det-math feature flags, the step count or the seed is
edited. It has no skip-on-missing-file path: these four files are the
deliverable, so their absence is a failure and not a skip.

These records have no `.bin` sibling under evidence/, so they are not a pair.
`python3 interop/triosckp_reader.py --verify-all evidence` does not visit them
and its pair count is unchanged by their presence (17 pairs before and after,
exit 0, output byte-identical), which is why they need no line in
evidence/SEALS.txt.
