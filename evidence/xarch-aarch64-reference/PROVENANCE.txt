Evidence package: the aarch64 macOS half of the cross-architecture comparison
=============================================================================

What this directory is
----------------------

The aarch64 macOS reference checkpoint of the one cross-architecture
comparison this project has ever made, copied byte-for-byte out of
`checkpoints/r5-adv-recheck/` so that it is TRACKED. Until this copy existed,
`git ls-files checkpoints` returned 0: the headline result of
`docs/CROSS-ARCH-DIVERGENCE.md` compared a tracked x86_64 artifact against an
UNTRACKED file on one laptop. Anyone who cloned this repository received half
of the experiment. That is the defect this directory closes, and it is worth
stating plainly rather than quietly fixing.

The paired x86_64 Linux arm is `evidence/xarch-run-30767491098/`, with its own
`PROVENANCE.txt`. Neither directory is regenerated by any script. If a byte
changes here, the evidence is gone, not updated.

The sidecar schema, as it actually is
-------------------------------------

Read from the file, not assumed. `12000.json` is
`trios-checkpoint-record/4`. The record schema at HEAD is
`trios-checkpoint-record/9` (`CHECKPOINT_RECORD_SCHEMA` in
`src/checkpoint.rs`). This artifact therefore carries an OLD record, and the
honest reading of an old record is the one `src/checkpoint.rs` states for
itself: a `/1`-`/8` record is SILENT about the fields it lacks, it does not
assert their default. Decide by FIELD PRESENCE.

The 34 top-level fields present:

  schema, canon_name, seed, step, path, sha256, bytes, format_version,
  hidden, d_model, num_attn_layers, vocab, optimizer, fake_quant_format,
  lr, attn_scale, attn_seq, gf16_floor_every, eval_every, data_synthetic,
  steps_total, final_val_bpb, best_val_bpb, ema_bpb, git_sha,
  git_provenance, git_dirty, corpus, source_sha256, trainer, platform,
  run_id, ledger, ts

`platform` carries six sub-fields: os, arch, pointer_width, libc,
toolchain, toolchain_provenance.

Fields a current (`/8` and later) record carries that THIS ONE DOES NOT, each
of which is a question this artifact cannot answer:

  top level
    val_bpb_stderr        how noisy the reported bpb is. Absent, so the
                          0.0030 bpb gap against the x86_64 arm has no
                          sidecar-local uncertainty; the sigma quoted in
                          docs/CROSS-ARCH-DIVERGENCE.md comes from
                          docs/EVAL-UNCERTAINTY.md, measured elsewhere.
    eval_chunks,          the sampling plan of the eval. Absent, so the
    eval_tokens,          reported bpb here does not describe how it was
    eval_seq              measured.
    gf16_enabled          whether the 1/16 grid was on. Absent from the

                          says "adamw" and not which AdamW.
    git_untracked         whether an untracked .rs was compiled in. Absent,
                          so this record is SILENT on that, not clean.
    min_observed_val_bpb  the field that replaced `best_val_bpb`.

  platform
    libc_version          "undetermined" is all this record says. A current

    features              the compiled feature set.

    remap_applied         decide `trainer.sha256`.

`git_dirty: true`, and why it does not reach the trainer bytes
--------------------------------------------------------------

The record says the working tree did not match `3c1f751...`. That is a real
disclosure and it is not waved away here. What limits it is a separate,
checkable fact:

  source_sha256  19aa22fb7cd187774b71cbde7cb89b664aff7260b57f55afd865dd4477
                 07108b

is IDENTICAL to the value the clean x86_64 CI arm recorded, and it is
reproducible today from the tracked tree. At `3c1f751` the digest domain was
`trios-source-tree/1` and its input set was exactly `src/**/*.rs` (115 files)
plus `Cargo.toml`. Recomputing that digest over `git archive 3c1f751`
reproduces `19aa22fb...` exactly. Run:

mkdir -p /tmp/d1 && git archive 3c1f751 | tar -x -C /tmp/d1 && cd /tmp/d1
python3 - <<'PY'
import hashlib, os
files = [os.path.join(r, f) for r, _, fs in os.walk('src')
         for f in fs if f.endswith('.rs')] + ['Cargo.toml']
h = hashlib.sha256(); h.update(b"trios-source-tree/1\n")
for p in sorted(files):
    raw = open(p, 'rb').read()
    h.update(len(p).to_bytes(8, 'little')); h.update(p.encode())
    h.update(len(raw).to_bytes(8, 'little')); h.update(raw)
print(h.hexdigest())
PY
# 19aa22fb7cd187774b71cbde7cb89b664aff7260b57f55afd865dd447707108b

So a DIRTY tree recorded the digest of the CLEAN tracked tree: at the moment
the trainer walked it, every `src/**/*.rs` and `Cargo.toml` was byte-identical
to `3c1f751`. The dirt was in files that are not compiler inputs.

State the limit of that argument in the same breath, because it is real:

  * The `/1` input set is NARROW. It does not cover `Cargo.lock`,
    `rust-toolchain.toml`, `migration/src/**/*.rs`, the compiled feature set,
    or `.cargo/config.toml`. A later `/3` digest covers all five. So this
    equality proves the Rust sources and the manifest matched; it does not
    prove the dependency lock or the build flags did.
  * `source_sha256` is a RUN-time walk of the working directory. It is not
    proven to be the tree the running binary was COMPILED from, as
    `resolve_source_digest` says of itself. It is strictly stronger than a
    commit hash over a dirty tree; it is not a build attestation.

`git_dirty` on this working tree is currently uninformative
-----------------------------------------------------------

Anyone re-running the trainer here today will get `git_dirty: true` no matter
what they change, and should not read it as a signal. As of 2026-08-05,
`git status --porcelain --untracked-files=no` reports 827 changed paths, of
which 779 are DELETIONS under `queen-hive-mcp/target/` - build output that was
committed once and has since been removed from disk. Spot-checked: the first
such path, `queen-hive-mcp/target/.rustc_info.json`, is tracked by git and
absent from the filesystem.

  git status --porcelain --untracked-files=no | wc -l                  # 827
  git status --porcelain --untracked-files=no \
    | grep -c '^ D queen-hive-mcp/target'                              # 779

Those 779 are 94% of the dirt, none of it a compiler input for this crate. The
flag is therefore permanently stuck at `true` on this host, which is exactly
why `source_sha256` and not `git_dirty` carries the argument above. It also
means the `git_dirty: true` in this artifact's sidecar is consistent with the
same stuck condition and is not evidence of a modified trainer.
